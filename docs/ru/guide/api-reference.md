# Справочник HTTP API :id=http-query-reference

Здесь описаны параметры запросов LifeUp Cloud и полные модели HTTP-ответов. Установку, авторизацию и подключение начните с [LifeUp Cloud](/guide/api_cloud). Новые эндпоинты журналов требуют LifeUp **1.106.0+** и LifeUp Cloud **3.0.0+**; установленные версии можно узнать через `/info`. Справочник описывает контракты текущего исходного кода и не подтверждает доступность в определённом релизе.

## Передача и представление данных :id=representations

| Интерфейс | Представление | Важное отличие |
| --- | --- | --- |
| HTTP-запросы Cloud | JSON в обёртке `{code, message, data}` | Справочники конечных точек ниже описывают этот публичный JSON. |
| Android ContentProvider | Столбцы Cursor, например `_ID` / `_GID`, иногда содержащие текст JSON | Парсер SDK преобразует их в поля HTTP, например `id` / `gid`, и вложенные массивы. Не используйте определения столбцов Cursor как схему HTTP. |
| Действия URL Scheme | `lifeup://api/{method}` и параметры/результаты конкретного метода | Параметры записи могут использовать snake_case, даже если поля чтения HTTP используют camelCase. |
| Инструменты списков MCP | Обёртка конкретного инструмента и сокращённые или подробные записи | Пагинация MCP и выходные поля — дополнительное поведение клиента, а не поля ответа HTTP. |

## Ответы и ошибки :id=response-errors

Общая JSON-обёртка HTTP — `HttpResponse<T>`:

| Поле | Тип | Значение |
| --- | --- | --- |
| `code` | integer | `200` при успешном запросе; значение, отличное от `200`, означает ошибку. Это поле тела ответа, отдельное от статуса HTTP. |
| `message` | string | Обычно `success` при успехе; иначе описание ошибки. |
| `data` | `T` или `null` | Значение эндпоинта (массив, объект или строка) при успехе; `null` при ошибке. |

Пример успешного ответа с пустым списком:

```json
{"code":200,"message":"success","data":[]}
```

Пример ошибки разрешения/доступа к провайдеру:

```json
{"code":10001,"message":"Cursor is null, check if LifeUp is installed and running and you have granted the permission","data":null}
```

| Сигнал | Обработка |
| --- | --- |
| HTTP `401` | Передайте настроенный токен Cloud как исходное значение заголовка `Authorization`. Не добавляйте `Bearer`. |
| `code = 10001` в теле | Проверьте, что LifeUp установлен/запущен, а Cloud имеет разрешение на чтение данных LifeUp. |
| `code = 10002` в теле | Запрос ContentProvider завершился ошибкой; изучите сообщение об ошибке. |
| Другой неуспешный статус/код | Считайте запрос неудачным, а не пустым результатом. |

Проверяйте **и** статус HTTP, **и** `code` в теле. Некоторые ошибки маршрутов возвращают HTTP `200` с кодом ошибки в теле. Для действий через `/api/contentprovider` дополнительно проверяйте каждый `data[].result.api_result`; `code=200` обёртки не доказывает успешность каждого действия.

## Авторизация и условное чтение :id=auth-cache

Если настроен токен Cloud, передавайте его точное исходное значение в `Authorization` без префикса `Bearer`. Сервер также принимает параметр запроса `token`, в том числе для клиентов, которые не могут задать заголовок WebSocket. Отсутствующий или неверный токен приводит к HTTP `401` и `code=401` в теле. Проверка охватывает стартовую страницу, ресурсы, мост, файлы, передачу резервных копий и события.

Успешное чтение JSON-ресурсов добавляет сильный SHA-256 `ETag` и `Cache-Control: private, no-cache`. Это относится к задачам/истории, предметам/категориям, навыкам/группам, достижениям/условиям, впечатлениям, синтезу/категориям, журналам, уровням, статистике, информации и монетам. Для моста вызовов, передачи файлов и резервных копий, потоков/опроса событий это не применяется.

| Заголовок запроса | Текущее поведение ответа |
| --- | --- |
| `If-Match` | Несовпадающая версия приводит к HTTP `412`; проверяется до `If-None-Match`. |
| `If-None-Match` | Совпадающая версия возвращает HTTP `304` без JSON-тела. Используйте ранее кэшированное успешное представление. |

Оболочки ошибок не содержат заголовка версии ресурса. Условное чтение действует для отдельного запроса и не создаёт снимок или транзакцию между страницами и маршрутами.

Браузерные запросы между источниками могут использовать `If-None-Match`. Текущая конфигурация CORS не разрешает `If-Match` при preflight, поэтому без изменения реализации не полагайтесь на такие браузерные запросы. На нативные клиенты браузерные ограничения CORS не распространяются.

## Общие соглашения о данных :id=data-conventions

| Соглашение | Правило |
| --- | --- |
| Время | Поля временных меток используют миллисекунды Unix. Границы календарного дня зависят от выбранного часового пояса. Значение каждого поля по-прежнему определяется его ресурсом. |
| Идентификация | `id` задачи обозначает одну задачу/цикл; `gid` задачи обозначает её группу в повторяющихся циклах. ID категории/списка обозначает отдельный ресурс. |
| Пустые значения | Отсутствие, `null`, `0`, `""` и `[]` различаются. Каждая модель описывает фактические подстановки и пропуски. |
| Числовые ID | ID могут быть знаковыми 64-битными целыми числами; JavaScript Number не может точно представить каждое значение. Сохраняйте большие ID с помощью подходящего JSON-парсера. |
| Массивы и объекты | Вложенные значения HTTP, например `items` и `subTasks`, — массивы, а не строки с JSON. |
| Коды статусов и причин | Используйте перечисление, описанное для конкретного ресурса. Статус задачи, статус достижения и коды причин журнала относятся к разным областям значений. |

Определения `startTime`, `deadline` и `endTime` см. в разделе [временных меток задачи](/guide/api-reference?id=task-times).

## Пагинация и фильтрация :id=pagination

Пагинация — возможность конкретной конечной точки, а не свойство любого списка. Исходные ответы списков HTTP содержат `data: [...]`; они **не** добавляют `total`, `count` или `hasMore`.

| Конечная точка HTTP | Пагинация | Диапазон дат | Другие фильтры |
| --- | --- | --- | --- |
| `/tasks`, `/tasks/{categoryId}` | Нет; полный массив | Нет | Необязательная категория в пути |
| `/history` | Серверные `offset` / `limit` | Нет | Необязательный `gid` |
| `/feelings` | Серверные `offset` / `limit` | Нет | См. [впечатления](#get-feelings) |
| `/pomodoro_records`, `/coin_records`, `/inventory_records`, `/exp_records`, `/step_records` | Серверные `offset` / `limit` | `time_range_start` / `time_range_end` | См. разделы соответствующих эндпоинтов ниже |
| `/statistics` | Нет; один объект | `time_range_start` / `time_range_end` | Агрегирующий запрос |
| `/coin`, `/info` | Нет; один объект | Нет | Запрос единственного объекта |

Для конечных точек с пагинацией значения HTTP по умолчанию — `offset=0` и `limit=100`. В общем цикле пагинации используйте неотрицательное смещение и размер страницы `1..100`. Мост HTTP не применяет ограничение MCP `1..100`, а нижележащие провайдеры могут вводить другие ограничения; сверяйтесь с эффективным размером страницы и правилами проверки каждой конечной точки.

За исключением [ограничения помидоров с фильтром времени](#get-pomodoro-records), после каждой успешной страницы увеличивайте `offset` на число полученных записей. Остановитесь, когда оно меньше фактического размера страницы (запрошенный `limit` при `1..100`, кроме помидоров с фильтром времени). Не принимайте страницу, ограниченную провайдером, за последнюю. Пустая страница за концом списка нормальна. Чтение нескольких страниц не создаёт снимок: записи могут изменяться во время запроса.

В текущем HTTP SDK границы дат передаются, только если **обе** разбираются как целые числа и `start < end`. Единственная граница, неразбираемое значение или обратный порядок приводят к запросу без фильтра; не рассчитывайте обнаружить это по ошибке. Проверяйте обе границы перед отправкой. Справочник журналов описывает включение обеих границ для соответствующих конечных точек.

## Отличия MCP :id=mcp-differences

Инструменты списков MCP по умолчанию используют `limit=20`, ограничивают его диапазоном `1..100`, а `offset` — снизу значением `0`. Для ресурсов с серверной пагинацией, например истории/журналов, они передают параметры пагинации серверу, а для ресурсов вроде задач получают полный массив HTTP и выделяют страницу локально. Их поля `items`, `count`, `hasMore` и необязательное `total` принадлежат обёртке MCP. `detail=false` также удаляет поля из каждой записи; если нужна полная модель HTTP, используйте `detail=true`.

## Модели данных задач и истории :id=task-history-models

Эта страница определяет **JSON HTTP**, возвращаемый [запросами задач/истории](/guide/api-reference?id=task-queries). Столбцы Android Cursor и параметры действий URL Scheme могут иметь другие имена и представления; см. [общие соглашения](/guide/api-reference?id=representations).

SDK использует один сериализуемый класс `Task` для двух представлений. Здесь `Task` обозначает представление `/tasks`, а `HistoryRecord` — представление `/history`. Эти имена описывают существующий вывод и не вводят ещё один API. Текущая сериализация Cloud включает значения по умолчанию и поля `null`.

### Поля Task / HistoryRecord :id=task-fields

Все перечисленные ниже поля присутствуют в текущем объекте HTTP. Отсутствующие значения провайдера часто преобразуются в указанные подстановки; подстановка не доказывает наличие такого значения в исходных данных.

| Поле | Тип JSON | Значение / подстановка |
| --- | --- | --- |
| `id` | integer или `null` | ID этой задачи/цикла. |
| `gid` | integer или `null` | ID группы задач, общий для повторяющихся циклов. |
| `name` | string | Название задачи. Отсутствующее название провайдера становится `ERROR: name is null`. |
| `notes` | string | Заметки; пустая строка при отсутствии. |
| `status` | integer | Статус задачи; при отсутствии используется `0`. См. таблицу статусов ниже. |
| `startTime` | integer | Настроенное время начала в миллисекундах; подстановка SDK `0`. |
| `deadline` | integer | Срок выполнения в миллисекундах; подстановка SDK при отсутствии — `0`. |
| `remindTime` | integer | Время напоминания в миллисекундах; подстановка SDK при отсутствии — `0`. |
| `frequency` | integer | Код повторения; `0` однократно, `1` ежедневно, `-1` без ограничений. Другие режимы описаны в [действиях с задачами](/guide/api). Подстановка SDK `0`. |
| `weekdays` | string | Выбранные дни недели, например `1,3,5` (понедельник `1`, воскресенье `7`); пустая строка, если не задано, а в истории — постоянная пустая заглушка. |
| `exp` | integer | Настроенная награда EXP, а не сумма транзакции; по умолчанию `0`. |
| `skillIds` | массив integer | Характеристики, связанные с наградой; пустой массив при недоступности. |
| `coin` | integer | Настроенная награда монетами; по умолчанию `0`. |
| `coinVariable` | integer | Настройка случайной награды монетами; по умолчанию `0`. |
| `itemId` | integer | Устаревшее поле ID первого предмета награды; по умолчанию `0`. Полный список см. в `items`. |
| `itemAmount` | integer | Устаревшее поле количества первого предмета награды; по умолчанию `0`. Это имя HTTP отличается от столбца провайдера `itemCount`. |
| `words` | string | Мотивирующий текст при завершении; пустая строка при отсутствии. |
| `categoryId` | integer | ID категории/списка задач; при отсутствии по умолчанию `0`. |
| `order` | integer | Значение порядка в списке задач; в истории — постоянная заглушка `0`, поскольку её провайдер не возвращает этот столбец. |
| `nameExtended` | string | Расширенное отображаемое название; в истории — постоянная пустая заглушка, поскольку её провайдер не возвращает этот столбец. |
| `endTime` | integer | Записанное время окончания для истории. `/tasks` заполняет его значением `0`; см. [значение времени](/guide/api-reference?id=task-times). |
| `items` | `RewardItem[]` | Награды предметами; пустой массив при недоступности. |
| `subTasks` | `SubTask[]` | Вложенные подзадачи; пустой массив при недоступности. |
| `countProgress` | `TaskCountProgress` или `null` | Снимок прогресса счётчика, если доступен; может присутствовать в обоих представлениях. |
| `repeatEndCondition` | `TaskRepeatEndCondition` или `null` | Правило окончания повторений в `/tasks`; всегда `null` в `/history`. |

### Статусы и временные метки задачи :id=task-times

| `status` | Значение | Значение `endTime` в истории |
| --- | --- | --- |
| `0` | Не завершена | Не время выполнения; `/history` выбирает записи закончившихся задач. |
| `1` | Выполнена | Записанное время выполнения. |
| `2` | Просрочена | Записанное время просрочки. |
| `3` | Отказ от выполнения | Записанное время отказа. |

| Поле времени | Определение |
| --- | --- |
| `startTime` | Настроенное/запланированное время начала задачи, а не момент фактического начала работы пользователя. |
| `deadline` | Запланированный срок выполнения, отдельный от записанного времени окончания. |
| `endTime` | Записанное время окончания задачи в истории; интерпретируется вместе со `status`, как описано выше. |

Все три поля используют миллисекунды Unix. При обычном выполнении App записывает текущее время. `history_operation` с `operation=edit_completed_time` принимает входное значение `completed_time` и изменяет это же сохранённое время выполнения; при чтении истории поле по-прежнему называется `endTime`.

Сохранённое время можно редактировать. Если у закончившейся записи нет сохранённой даты окончания, App использует текущее время. Поэтому `endTime` — текущее записанное время, а не неизменяемая аудиторская метка. `0` в `/tasks` — лишь заглушка SDK, а не реальное событие в начале эпохи Unix.

## Запросы задач и истории :id=task-queries

Прочитайте [общие соглашения](/guide/api-reference?id=http-query-reference) и [полную модель Task/History](/guide/api-reference?id=task-history-models). Для этих конечных точек Cloud требуется разрешение на чтение данных LifeUp. Базовые запросы списков описаны для LifeUp v1.91+ с последней версией Cloud; примеры показывают поля текущего SDK. При интеграции со старыми установками проверяйте `/info`.

### GET /tasks и /tasks/{categoryId} :id=get-tasks

Запрашивает текущий список **незавершённых** задач с необязательным ограничением по категории/списку. Результат — полный массив, а не ответ с серверной пагинацией. Выполненные, просроченные задачи и записи об отказе от выполнения находятся в `/history`.

| Параметр | Расположение | Тип | Обязателен | По умолчанию / поведение |
| --- | --- | --- | --- | --- |
| `categoryId` | Путь | integer | Только для `/tasks/{categoryId}` | Для списка без ограничений опустите весь сегмент пути. |

Эти маршруты не поддерживают параметры запроса `offset`, `limit`, `gid` и диапазон дат. Сегмент категории, который не является целым числом, сейчас разбирается как отсутствие категории; проверяйте его до запроса, чтобы случайно не запросить все задачи.

```text
GET http://{host:port}/tasks
GET http://{host:port}/tasks/1
```

**Ответ:** `HttpResponse<Task[]>`. Все поля записей и вложенные структуры определены в [полях Task/History](/guide/api-reference?id=task-fields). Следующая вымышленная запись показывает полную структуру HTTP верхнего уровня; `endTime=0` — заглушка этого маршрута, а не временная метка выполнения.

```json
{
  "code": 200,
  "message": "success",
  "data": [{
    "id": 101, "gid": 10, "name": "Read a chapter", "notes": "",
    "status": 0, "startTime": 1792108800000, "deadline": 1792195199999,
    "remindTime": 0, "frequency": 1, "weekdays": "",
    "exp": 5, "skillIds": [2], "coin": 10, "coinVariable": 0,
    "itemId": 0, "itemAmount": 0, "words": "", "categoryId": 1,
    "order": 0, "nameExtended": "Read a chapter", "endTime": 0,
    "items": [], "subTasks": [], "countProgress": null,
    "repeatEndCondition": null
  }]
}
```

**Поведение и ошибки:** выбор и порядок списка следуют логике списка задач LifeUp; конечная точка не гарантирует сортировку по времени выполнения. Успешный `data: []` означает, что выбранный список задач не вернул записей. Ошибки разрешений/провайдера используют [общую обёртку ошибок](/guide/api-reference?id=response-errors), а не пустые массивы. Для отчётов о выполнении используйте `/history` ниже, а не `endTime` этого маршрута.

### GET /history :id=get-history

Запрашивает видимые записи закончившихся задач, включая выполненные, просроченные и задачи с отказом от выполнения. Удалённая история исключается.

| Параметр | Расположение | Тип | Обязателен | По умолчанию / поведение |
| --- | --- | --- | --- | --- |
| `offset` | Запрос | integer | Нет | `0`; число пропускаемых записей, начиная с нуля. |
| `limit` | Запрос | integer | Нет | `100`; запрашивайте положительный размер страницы, желательно `1..100`. |
| `gid` | Запрос | integer | Нет | Без фильтра группы; если указан, выбирает эту группу задач во всех циклах. |

Парсер HTTP подставляет `0` / `100`, если `offset` / `limit` не разбираются, и отбрасывает неразбираемый `gid`. Этот маршрут не ограничивает успешно разобранные числа. Самостоятельно проверяйте неотрицательные смещения и положительные лимиты. `time_range_start` / `time_range_end` **не поддерживаются**; их передача не фильтрует историю.

```text
GET http://{host:port}/history?offset=0&limit=100
GET http://{host:port}/history?offset=0&limit=100&gid=10
```

**Ответ:** `HttpResponse<HistoryRecord[]>` с [передаваемыми полями Task/History](/guide/api-reference?id=task-fields). `HistoryRecord` — имя в документации для представления истории модели `Task` SDK. `repeatEndCondition` в этом представлении равно `null`; `countProgress` может присутствовать. Сохранённое `endTime` интерпретируется вместе со `status`.

```json
{
  "code": 200,
  "message": "success",
  "data": [{
    "id": 100, "gid": 10, "name": "Read a chapter", "notes": "",
    "status": 1, "startTime": 1792022400000, "deadline": 1792108799999,
    "remindTime": 0, "frequency": 1, "weekdays": "",
    "exp": 5, "skillIds": [2], "coin": 10, "coinVariable": 0,
    "itemId": 0, "itemAmount": 0, "words": "", "categoryId": 1,
    "order": 0, "nameExtended": "", "endTime": 1792072800000,
    "items": [], "subTasks": [], "countProgress": null,
    "repeatEndCondition": null
  }]
}
```

**Порядок:** по сохранённой дате окончания по убыванию, сначала новые. Дополнительный порядок для одинаковых дат окончания не документирован. Пагинация не создаёт снимок данных; избегайте редактирования во время сбора отчёта и удаляйте дубликаты по `id` при объединении страниц.

**Пагинация и пустые результаты:** используйте [общую процедуру пагинации](/guide/api-reference?id=pagination). Успешный пустой массив означает отсутствие подходящих видимых записей на этой странице/в группе, в том числе когда `offset` вышел за конец списка. Это не подтверждает отсутствие активности за всё время: удалённые записи исключены, а признака полноты нет. Если любой запрос завершился ошибкой, сообщайте о недоступных/неполных данных, а не о нуле задач. Действуют [общие ошибки](/guide/api-reference?id=response-errors).

### Создание ежедневного отчёта :id=daily-report

1. Выберите часовой пояс отчёта. Вычислите начало календарного дня (`dayStart`) и начало следующего календарного дня (`nextDayStart`). Не предполагайте, что каждый местный день длится ровно 24 часа.
2. Читайте `/history` с `offset=0&limit=100`, проверяйте каждый ответ и собирайте все страницы. Сохраняйте выбранный фильтр `gid` неизменным.
3. Выберите `status == 1` и `dayStart <= endTime < nextDayStart`. При описании результатов учитывайте [ограничения записанного времени](/guide/api-reference?id=task-times).
4. Для фактических изменений EXP и монет прочитайте [журналы наград](/guide/api-reference?id=reward-journals) за тот же день. Их фильтры включают обе границы, поэтому используйте `time_range_start=dayStart` и `time_range_end=nextDayStart-1`.
5. Отличайте «в доступных данных записи не найдены» от неудачного/незавершённого чтения. Решите, показывает ли отчёт только положительные награды или чистые изменения с отменами, и применяйте это решение последовательно.

`exp` и `coin` задач/истории — настроенные награды; они не являются надёжной заменой суммам из журналов. Перенос времени выполнения на другой день не означает, что вместе с ним изменилось время транзакции в журнале наград.

## Запросы журналов EXP и монет :id=reward-journals

Эти HTTP-конечные точки только для чтения требуют разрешения на чтение данных LifeUp, LifeUp **1.106.0+** и LifeUp Cloud **3.0.0+**. Они возвращают записанные изменения, включая уменьшения и отмены, а не настройки наград задач. Сначала прочитайте [общие соглашения](/guide/api-reference?id=http-query-reference).

### Параметры запросов обеих конечных точек :id=journal-parameters

Следующий контракт относится именно к **обеим** конечным точкам `GET /exp_records` и `GET /coin_records`.

| Параметр | Расположение | Тип | Обязателен | По умолчанию / фактическое поведение |
| --- | --- | --- | --- | --- |
| `offset` | Запрос | integer | Нет | Значение HTTP по умолчанию `0`; провайдер ограничивает отрицательные значения до `0`. |
| `limit` | Запрос | integer | Нет | Значение HTTP по умолчанию `100`; провайдер ограничивает диапазоном `1..200`. Для общей процедуры пагинации используйте `1..100`. |
| `time_range_start` | Запрос | integer (миллисекунды Unix) | Нет, либо в паре | Включительная нижняя граница записанного времени транзакции. |
| `time_range_end` | Запрос | integer (миллисекунды Unix) | Нет, либо в паре | Включительная верхняя граница; корректная фильтрация требует `start < end`. |

Неразбираемые или выходящие за диапазон значения пагинации заменяются значениями HTTP по умолчанию. Неразбираемые даты считаются отсутствующими. Текущий SDK передаёт диапазон дат, только если обе границы заданы и `start < end`; иначе выполняется запрос **без фильтра дат**. Прямые необработанные вызовы ContentProvider иначе проверяют некорректные диапазоны. Проверяйте границы в вызывающем HTTP-клиенте.

Обе конечные точки сортируют по записанному времени транзакции по убыванию, сначала новые, и исключают удалённые записи журналов. Они не гарантируют дополнительный порядок по ID или снимок данных для нескольких страниц. Следуйте правилам [пагинации](/guide/api-reference?id=pagination), учитывая эффективный лимит провайдера. Успешный пустой массив означает отсутствие записей в выбранном диапазоне/на странице; ошибка чтения не означает нулевую активность. Ни одна конечная точка не предоставляет признак полноты для удалённых или недоступных данных.

### GET /exp_records :id=get-exp-records

Запрашивает изменения EXP. Параметры — ровно [четыре параметра журналов выше](/guide/api-reference?id=journal-parameters); фильтра `gid` нет.

```text
GET http://{host:port}/exp_records?offset=0&limit=100&time_range_start=1792022400000&time_range_end=1792108799999
```

**Ответ:** `HttpResponse<ExpRecord[]>`. Текущая сериализация включает все перечисленные поля, в том числе допускающие null.

| Поле | Тип JSON | Значение / подстановка парсера |
| --- | --- | --- |
| `id` | integer или `null` | ID записи журнала. |
| `time` | integer или `null` | Время транзакции в миллисекундах Unix, отдельное от редактируемого времени выполнения задачи. |
| `value` | integer | Изменение EXP для каждой связанной характеристики; подстановка `0`. Направление определяется `isDecrease`. |
| `isDecrease` | boolean | `true` для уменьшения, `false` для увеличения; парсер считает целое значение провайдера `1` истинным. |
| `totalValue` | integer | Записанное суммарное изменение EXP, **не баланс EXP**; подстановка `0`. Пакеты нескольких характеристик могут перекрываться в этой сохранённой сумме; см. [итоги отчётов](/guide/api-reference?id=journal-totals). |
| `resCode` | integer | Код причины для EXP; подстановка `0`. |
| `relatedId` | integer или `null` | ID связанного исходного объекта. При обычном выполнении задачи это `id` записи задачи, а не её `gid`. Другие причины могут ссылаться на другие ресурсы. |
| `content` | string или `null` | Описание изменения. |
| `skillIds` | массив integer | ID связанных характеристик/навыков; подстановка — пустой массив. |
| `relatedAttributes` | массив string | Связанные устаревшие строковые обозначения характеристик; подстановка — пустой массив. |

Вымышленный пример: по 10 EXP для каждой из двух характеристик, всего 20 EXP.

```json
{
  "code":200,"message":"success","data":[{
    "id":301,"time":1792072800000,"value":10,"isDecrease":false,
    "totalValue":20,"resCode":1,"relatedId":100,"content":"Task completed",
    "skillIds":[2,3],"relatedAttributes":[]
  }]
}
```

**Ошибки:** [общие ошибки HTTP/провайдера](/guide/api-reference?id=response-errors). Некорректные границы дат HTTP могут незаметно отключить фильтрацию, как описано выше, вместо возврата ошибки.

### Коды причин и итоги отчётов :id=journal-totals

Области кодов причин различаются. Некоторые примеры:

| Причина | EXP `resCode` | Монеты `resCode` |
| --- | --- | --- |
| Выполнение задачи | `1` | `2` |
| Отмена выполнения задачи | `101` | `3` |
| Выполнение подзадачи | `12` | `11` |
| Отмена выполнения подзадачи | `106` | `12` |
| Изменение через API | `200` | `28` |

Полные коды EXP: `0` неизвестно; `1` завершение задачи; `2` достижение; `3` обмен лайков; `4` серия дней использования; `5` обмен шагов; `6` отметка завершения; `7` отмена отказа; `8` отмена просрочки; `9` съесть помидор; `10` использовать предмет; `11` разблокировка пользовательского достижения; `12` завершение подзадачи; `200` API; `101` отмена завершения; `102` отказ; `103` просрочка; `104` использование предмета уменьшает EXP; `105` повторная блокировка пользовательского достижения; `106` отмена завершения подзадачи. Коды причин для монет используют ту же область значений, что [записи инвентаря](#get-inventory-records). Сохраняйте неизвестные будущие коды. Для чистого изменения применяйте направление через `isDecrease` (`true` вычитает записанную величину). Не считайте, что уменьшение закодировано отрицательным `value`: числовые типы знаковые, гарантия беззнакового/абсолютного значения отсутствует.

`value` EXP относится к каждой характеристике. Не суммируйте вслепую `totalValue` EXP между записями: текущая пакетная обработка нескольких характеристик может сохранять перекрывающиеся суммы, если характеристик больше трёх. Например, изменение четырёх характеристик на 10 EXP каждой может дать сохранённые суммы 40 и 10, которые нельзя безопасно сложить для получения 40. Для точных отчётов сопоставляйте `value` каждой характеристики с характеристиками, указанными в каждой записи; отсутствие связей ограничивает достоверные выводы. Не складывайте `value` и `totalValue` и не называйте `totalValue` EXP балансом.

Для одного календарного дня вычислите местные `dayStart` и `nextDayStart`, затем запросите `[dayStart, nextDayStart - 1]`, поскольку обе границы включены. Выбирайте коды причин, когда отчёт охватывает только награды задач; для всех записанных изменений не фильтруйте причины. [Процедура ежедневного отчёта](/guide/api-reference?id=daily-report).

## Предметы и категории :id=get-items

`GET /items` возвращает `ShopItem[]`. Необязательный повторяемый параметр `id` выбирает ID предметов: `/items?id=1&id=2`. Нецелые значения отбрасываются. Несуществующие ID пропускаются; действительные сохраняют порядок запроса, включая дубликаты. Если все переданные ID некорректны, SDK не отправляет фильтр ID и возвращается обычный список предметов. Разбиения на страницы нет.

`GET /items/{listId}` возвращает `ShopItem[]` из **категории**, а не отдельный предмет. `listId` — знаковый 64-битный ID категории; `-1` означает все. Выбор по ID позволяет получить предмет независимо от фильтра обычного списка.

## Записи помидоров :id=get-pomodoro-records

`GET /pomodoro_records` возвращает `PomodoroRecord[]`. `offset` по умолчанию 0, `limit` — 100; явного ограничения нет. Необязательные `time_range_start` и `time_range_end` задаются в миллисекундах Unix. SDK передаёт диапазон, только если обе границы распознаны как 64-битные целые и начало меньше конца; иначе диапазон молча опускается.

Без диапазона возвращаются завершённые неудалённые записи с `startTime != endTime` и положительным `endTime` в порядке `endTime DESC, startTime DESC, id DESC`. Корректный диапазон выбирает `start < endTime <= end` и исключает удалённые строки.

> [!WARNING]
> В прежней реализации запросы диапазона дат передавали `limit` и `offset` в DAO в обратном порядке и не задавали сортировку. Локальный код LifeUp исправлен: используются именованные аргументы, а страницы сортируются по `endTime DESC, startTime DESC, id DESC`; это локальное исправление ещё не опубликовано. Пока вы не подтвердили его наличие в установленной версии LifeUp, для надёжного чтения страниц опускайте диапазон и фильтруйте строки на клиенте.

```json
{"code":200,"message":"success","data":[{"id":1,"startTime":1700000000000,"endTime":1700001500000,"duration":1500000,"reward":1.0}]}
```

## Записи инвентаря :id=get-inventory-records

`GET /inventory_records` возвращает `InventoryRecord[]`. `offset` по умолчанию 0 и ограничен снизу 0; `limit` по умолчанию 100 и ограничен диапазоном 1–200. ## Вызов API URL Scheme :id=invoke-api

[Каталог API URL Scheme](/guide/api) определяет названия методов, их параметры и результаты. Мост HTTP принимает полный URL `lifeup://api/...`.

| Транспорт | Входные данные | Выполнение и ответ |
| --- | --- | --- |
| `GET /api` | Повторяемый параметр `url` с URL-кодированием | Запускает Android Activity для каждого URL в переданном порядке. Возвращает строку `success`. При отсутствии URL тоже возвращает успех. |
| `POST /api` | JSON `RawQueryVo` | Сначала запускает все элементы `urls`, затем `url`, если он указан. Возвращает строку `success`. Пустой входной объект тоже успешен. |
| `GET /api/contentprovider` | Повторяемый параметр `url` с URL-кодированием | Синхронно вызывает провайдер и возвращает `CallUrlResult[]` в переданном порядке. При отсутствии URL возвращается оболочка ошибки (`No url found`). |
| `POST /api/contentprovider` | JSON `RawQueryVo` | Сначала вызывает все элементы `urls`, затем `url`; возвращает `CallUrlResult[]`. Пустой объект возвращает пустой массив. |

Для JSON POST задайте `Content-Type: application/json`. При передаче в GET-запросе закодируйте весь URL, сохраняя внутренние `&`, `?`, `+` и процентное кодирование. Успех моста Activity подтверждает отправку, а не завершение действия LifeUp. Методы ContentProvider требуют разрешения Cloud в LifeUp, поддержка зависит от метода URL Scheme. Вызовы последовательны; если последующий вызов выбросит исключение, предыдущие эффекты не откатываются.

```json
{"urls":["lifeup://api/query?key=coin"],"url":"lifeup://api/query?key=atm"}
```

Ответ моста через Activity:

```json
{"code":200,"message":"success","data":"success"}
```

Ответ моста через провайдер (пример результата провайдера):

```json
{"code":200,"message":"success","data":[{"url":"lifeup://api/query?key=coin","result":{"value":50,"api_result":true}},{"url":"lifeup://api/query?key=atm","result":{"value":100,"api_result":true}}]}
```

### RawQueryVo :id=model-raw-query

| Поле | Тип JSON | Значение |
| --- | --- | --- |
| `url` | строка или null | Необязательный одиночный URL. |
| `urls` | строка[] или null | Необязательный список URL; обрабатывается до `url`. |

### CallUrlResult :id=model-call-url-result

| Поле | Тип JSON | Значение |
| --- | --- | --- |
| `url` | string | Переданный URL. |
| `result` | объект или null | Преобразованный Bundle провайдера; null само по себе не означает ошибку HTTP-оболочки. |

Преобразование Bundle сохраняет значения Int/Long/Double/String/Boolean и вложенные Bundle. Массивы превращаются в массивы строк. Другие типы становятся строкой `toString()` (включая null Bundle, который становится строкой `"null"`). Поля ошибок метода внутри `result` нужно проверять даже при коде 200 внешней оболочки.

Текущий обработчик методов LifeUp добавляет `api_result` (логическое значение) к завершённым вызовам. Перехваченная ошибка метода возвращает `api_result: false`, `error_code` (строка) и `error_message` (строка). Коды включают `missing_required_parameter`, `invalid_parameter`, `entity_not_found`, `invalid_format`, `unsupported_api`, `cancelled` и `internal_error`; отдельные методы могут возвращать дополнительные коды. При восстановлении резервной копии провайдер может вернуть `error_code: "503"` и `error_message` без `api_result`. Отсутствующий обработчик API может выбросить исключение до этого преобразования, вызвав внешнюю ошибку моста.

## Чтение и загрузка файлов :id=files-download

### GET /files/{url} :id=files-get

Закодируйте полный доступный для чтения URI как один сегмент пути. Байты читаются через Android content resolver, обычно для значков, вложений впечатлений, экспортированных резервных копий и загруженных файлов. Результат — поток байтов, а не JSON-оболочка успеха. Маршрут не задаёт имя файла или MIME-тип. Пустые/нечитаемые потоки не преобразуются в структурированный результат «не найдено»; исключения обрабатываются глобальным обработчиком HTTP 500. Пустой сопоставленный параметр возвращает оболочку ошибки (`url is required`).

```bash
curl "$BASE/files/content%3A%2F%2Fexample.provider%2Fimages%2F1" -o image.bin
```

### POST /files/upload :id=files-upload

Передайте `multipart/form-data`. Принимаются все файловые части независимо от имени поля; остальные части формы игнорируются. Для файла кэша используется исходное имя; при его отсутствии Cloud выбирает `uploaded_image_<time>.jpg`. Возвращается массив строк доступных для чтения content URI. Загрузка даёт URI файла для последующих вызовов API и не прикрепляет его автоматически к предмету или задаче. Без файлов возвращается оболочка ошибки `No files received`.

```bash
curl -X POST "$BASE/files/upload" -F 'file=@image.png'
```

```json
{"code":200,"message":"success","data":["content://example.fileprovider/cache/image.png"]}
```

## Экспорт и импорт резервных копий :id=files-backup

### GET /data/export :id=files-export

Запускает создание резервной копии через провайдер. Необязательный `withMedia` по умолчанию `true`; если указан, `true` без учёта регистра означает истину, всё остальное — ложь. Возвращает преобразованный Bundle провайдера, сейчас содержащий `backup_file_uri`; скачайте URI через `/files/{url}`. Эндпоинт создаёт экспорт, несмотря на метод GET. Также могут присутствовать поля состояния/ошибки API провайдера, их нужно проверить. Пустой `backup_file_uri` означает отсутствие пригодного файла. Результат null становится ошибкой.

```json
{"code":200,"message":"success","data":{"backup_file_uri":"content://example.provider/backup/LifeUpExportBackup.zip","api_result":true}}
```

### POST /data/import :id=files-import

Передайте `multipart/form-data` с файлом резервной копии. Если файлов несколько, используется последний; имя поля не проверяется. Имя по умолчанию — `backup.lfbak`. Необязательное поле формы `description` читается, но не влияет на результат. Cloud кэширует файл и запускает Activity резервного копирования LifeUp; ответ подтверждает загрузку и запуск, **а не завершение восстановления**. Без файла возвращается `No file received`.

```bash
curl -X POST "$BASE/data/import" -F 'file=@backup.lfbak'
```

```json
{"code":200,"message":"success","data":"File uploaded and BackupActivity launched"}
```

## События :id=get-events

### GET /events :id=get-events-poll

Возвращает `EventsPage`. `after` — исключающий курсор ID события (64-битное целое, по умолчанию 0). `limit` — целое, по умолчанию 50, ограниченное 1–200. Нецелые значения заменяются значениями по умолчанию. В сохранённом буфере события идут от старых к новым с `id > after`. В памяти хранятся не более 200 событий; старые удаляются, перезапуск процесса сбрасывает ID. `latestId` — последний доступный глобальный ID, не обязательно последнее событие ограниченной страницы. Продолжайте с последнего реально обработанного события, чтобы не пропустить накопившиеся. Постоянной истории и подтверждения доставки нет.

```json
{"code":200,"message":"success","data":{"latestId":2,"eventWs":true,"events":[{"id":1,"time":1700000000000,"action":"app.lifeup.task.complete","extras":{"id":"42"}}],"broadcasts":true}}
```

### EventsPage :id=model-events-page

| Поле | Тип JSON | Значение |
| --- | --- | --- |
| `latestId` | integer | Текущий ID последнего события. |
| `eventWs` | boolean | Настройка WebSocket в Cloud. |
| `events` | CloudEvent[] | Сохранённые события после курсора. |
| `broadcasts` | логическое значение или null | Включены ли широковещательные сообщения LifeUp; null означает неизвестно или не поддерживается. Результат проверки кэшируется на пять секунд. |

### CloudEvent :id=model-cloud-event

| Поле | Тип JSON | Значение |
| --- | --- | --- |
| `id` | integer | Порядковый ID события в памяти. |
| `time` | integer | Unix-время получения в Cloud в миллисекундах. |
| `action` | string | Действие широковещательного сообщения Android. |
| `extras` | объект со строковыми значениями | Дополнительные данные сообщения, преобразованные через `toString()`; null становится пустой строкой. Ключи зависят от действия. |

### WebSocket /events :id=get-events-websocket

При `eventWs` true подключитесь к `ws://HOST:PORT/events?after=ID` с настроенным токеном. Сервер повторяет сохранённые события после `after`, затем отправляет новые отдельными текстовыми JSON-кадрами `CloudEvent` **без** оболочки HTTP-ответа. Повтор ограничен буфером на 200 событий; параметра WebSocket `limit` нет. Сервер посылает Ping каждые 30 секунд. Переподключайтесь с ID последнего реально обработанного события. При отключении маршрут WebSocket не регистрируется; опрос HTTP остаётся доступным.

```json
{"id":2,"time":1700000001000,"action":"app.lifeup.item.use","extras":{"id":"3"}}
```

Поддерживаются подписки на действия: `app.lifeup.task.complete`, `app.lifeup.task.overdue`, `app.lifeup.task.giveup`, `app.lifeup.achievement.unlock`, `app.lifeup.achievement.condition.unlock`, `app.lifeup.item.purchase`, `app.lifeup.item.reward`, `app.lifeup.item.use`, `app.lifeup.synthesis.complete`, `app.lifeup.pomodoro.start`, `app.lifeup.pomodoro.pause`, `app.lifeup.pomodoro.complete`, `app.lifeup.pomodoro.stop`, `app.lifeup.feelings.add`, `app.lifeup.level.up`, `app.lifeup.level.down`, `app.lifeup.item.countdown.start`, `app.lifeup.item.countdown.complete`, `app.lifeup.item.countdown.stop`, `app.lifeup.timing.start`, `app.lifeup.timing.complete`, `app.lifeup.timing.pause` и `app.lifeup.timing.abandon`. Для сбора событий нужно включить широковещательные сообщения LifeUp. Опрос `/events` проверяет эту настройку, но не включает её автоматически.
